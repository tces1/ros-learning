T6　性能与稳定性测试

功能正确只是第一步。机器人的控制回路要按时运行，避障要在几十毫秒内响应，系统要连续工作几十个小时不崩溃、不泄漏内存。本篇讲如何度量频率、延迟和资源占用，如何做长稳测试，以及如何主动注入故障，检验系统在异常下是否安全。

阅读 + 动手约 4 小时测试篇前置：第 4、11 章、T3、T4

本篇目标

  • 理解机器人系统的关键性能指标，并能正确度量与报告
  • 编写消息延迟探针和「障碍出现到停车」的反应时间测试
  • 监控进程 CPU、内存、线程、文件句柄，分析长稳测试中的内存增长
  • 设计并执行故障注入：进程崩溃、传感器中断、网络劣化、CPU 过载
  • 把性能指标接入 CI 门禁

报告百分位数，不要只报平均值

平均延迟 8 ms 的系统可能有 1% 的消息延迟 200 ms，而机器人恰恰在这 1% 的时刻撞上障碍。延迟类指标至少报告 p50、p95、p99 和最大值，并注明样本数、测试时长和硬件。

T6.2 命令行快速检查

命令行工具本身也有开销

ros2 topic hz 是 Python 实现的，对高频大消息（如点云、图像）可能处理不过来，测出的频率偏低。高频话题用 C++ 工具或在被测节点内部统计；同时记得这些工具会给被测话题增加一个订阅者。

一个通用的探针节点：订阅任意带 header 的话题，统计消息年龄和到达间隔，运行指定时长后输出百分位数并保存 CSV：

跨机器测延迟，先同步时钟

消息年龄 = 本机时间 − 发送方写入的时间戳。如果发送方在另一台机器上（例如雷达驱动在机器人上，探针在笔记本上），两台机器的时钟差会直接加到结果里，甚至出现负延迟。测试前用 chrony / PTP 同步时钟，并确认偏差远小于要测的延迟。仿真中两边都使用 use_sim_time。

T6.4 反应时间测试：障碍出现到停车

消息年龄只反映单个话题。对安全功能，真正关心的是「从看到障碍到发出停车指令」的端到端时间。下面的脚本对运行中的 safety_stop 做 50 次试验：先发送前方空旷的雷达数据和前进指令，然后突然切换为前方有障碍，测量收到第一条零速度输出的时间。

反应时间要在目标硬件上测

开发机的结果只能说明「算法没有明显的性能问题」。机器人上的工控机或嵌入式板卡性能可能只有开发机的几分之一，同时还在跑导航、感知、录包。验收数据必须来自目标硬件、完整负载下的测试。

T6.5 资源监控

关键字匹配的注意事项

ros2 run 会先启动一个包装进程再启动真正的节点，两者命令行都包含节点名，监控结果中可能出现两条记录，以 CPU 和内存较大的那个为准。CPU 百分比是相对单个核心的，多线程进程可能超过 100%。

T6.7 故障注入

主动制造故障，验证系统在异常下的行为是否符合设计。每个故障注入用例都要写清：注入什么、怎么注入、期望系统怎么反应、怎么判定。

故障注入方法期望行为（示例）
节点崩溃pkill -9 -f safety_stop底盘在指令超时（如 0.5 s）内停车；若配置了重启，5 s 内恢复
传感器中断停止雷达驱动或仿真中的 ros_gz_bridgesafety_stop 禁止前进；Nav2 报错并停止；诊断信息变为 ERROR

一个典型的故障注入发现：下游没有指令超时

在仿真中杀掉 safety_stop，你可能会发现小车继续以最后的速度前进，直到撞墙。原因是 Gazebo 的 DiffDrive 插件会一直执行最后收到的速度指令。真实底盘驱动和 ros2_control 的 diff_drive_controller（参数 cmd_vel_timeout）都应该有指令超时。任何发出运动指令的链路，最末端都必须有超时停车，这是实机测试前必须验证的项目。

同一台机器上的通信可能绕过网络

DDS 在同一台主机内常使用共享内存传输，tc 对它不起作用。要测试网络劣化的影响，应该让发布方和订阅方运行在两台机器上（例如机器人与遥控终端），在真实网卡上注入。

用 launch 配置自动重启并测量恢复时间

测量方法：pkill -9 的同时记录时间，用延迟探针或 ros2 topic echo 观察 /cmd_vel 何时恢复输出。重启后要检查：参数是否恢复（未持久化的运行时参数修改会丢失）、状态是否正确（例如巡逻进度）。

T6.8 深入分析：ros2_tracing

当需要知道「延迟花在哪一步」时（回调排队、执行、DDS 传输），可以使用 ros2_tracing。它基于 LTTng，在 rclcpp / rcl / rmw 的关键位置埋点，开销很低，可以在目标硬件上使用。基本流程：开启跟踪会话（ros2 trace）、运行系统、结束会话，再用 tracetools_analysis 或 Trace Compass 分析回调耗时和消息流。具体安装和参数以官方文档为准。

T6.9 性能门禁

把关键性能指标接入 CI，防止性能悄悄退化。思路是保存基线，每次运行与基线比较，超出容差即失败：

共享 CI 机器上的性能数据噪声很大

云端 CI 的虚拟机性能波动可达数十个百分点，所以容差要设得比较宽（如 50%），只用来发现「数量级」的退化。精确的性能回归应在固定的专用机器（最好是目标硬件）上定时运行，并把每次的结果画成趋势图。

动手练习

  1. 用延迟探针测量仿真中 /scan 的消息年龄和频率，分别在空闲和 stress-ng 满载时测试，比较 p95 和最大值。
  2. 运行反应时间测试，然后在 safety_stop 的 on_scan 中加入 time.sleep(0.05) 模拟慢算法，观察结果如何变化。
  3. 让巡逻系统运行至少 2 小时，同时运行资源监控，用 analyze_soak 分析结果。
  4. 在仿真中杀掉 safety_stop，观察小车行为；思考并写下应在哪一层增加指令超时。

自测题

1. 为什么延迟要报告 p95 / p99 / 最大值，而不只是平均值？
机器人的安全风险来自最坏情况。平均值会被大量正常样本稀释，掩盖偶发的长延迟；而避障恰恰需要在每一次都及时响应。百分位数和最大值才能反映尾部风险。
2. 跨机器测得的消息年龄是负数，说明什么？
两台机器时钟不同步：接收方时钟落后于发送方。需要先用 chrony 或 PTP 同步时钟，再进行延迟测量。
3. 长稳测试中某进程 RSS 前 10 分钟从 80 MB 涨到 150 MB，之后 8 小时稳定在 150–152 MB，有泄漏吗？
大概率没有。前 10 分钟是加载与缓存建立的预热阶段；之后斜率约 0.25 MB/h，在正常波动范围内。判断泄漏要看预热后的长期斜率。
4. 为什么「下游指令超时」是实机测试前必须验证的？
上游任何一个节点崩溃、卡死或网络中断，都会让运动指令停止更新。如果底盘一直执行最后一条指令，机器人会失控运动。底盘侧的超时停车是最后一道防线，与上游软件是否正确无关。
