T8　综合项目：为巡逻小车建测试体系

把 T1–T7 的方法用在第 16 章的巡逻小车上：制定测试策略，补齐各层自动化测试，用假导航器发现巡逻管理器的并发缺陷，搭建 CI 流水线，最后产出测试报告和缺陷报告。完成后，你将拥有一个可以在面试中完整讲述的机器人测试项目。

建议用时 1–2 周测试篇前置：第 16 章、T1–T7

T8.4 单元测试补充

test_parse_waypoints_non_numeric 会失败：len(['a','b','c',1]) % 3 不为 0，函数抛出的是 ValueError 而不是 TypeError。这说明测试用例本身也会写错——测试失败时，先判断是被测代码错了还是测试错了。这里应把用例改成 6 个元素（如 ['a', 'b', 'c', 1, 2, 3]），再观察 parse_waypoints 对非数字是否有校验（没有校验——参数类型由 ROS 参数系统保证为 double 数组，可以接受）。

假导航器实现巡逻管理器用到的 BasicNavigator 接口子集，并记录调用情况。它还统计「同时有几个线程在等待任务完成」，用来发现并发问题：

DEFECT-022 的成因与修复

 时间 ─────────────────────────────────────────────────────────────────►
 巡逻线程 A： followWaypoints ─ isTaskComplete … isTaskComplete … (继续导航，从未取消)
 服务回调：            stop: running.clear()   start: running 未置位 → running.set()，启动线程 B
 巡逻线程 B：                                     followWaypoints ─ isTaskComplete …
                                    ▲
                      线程 A 在两次检查之间错过了 running 被清除的窗口，
                      看到 running 又被置位，于是认为「仍在巡逻」，不会取消任务

结果是两个线程同时调用同一个 BasicNavigator：互相覆盖目标、圈数被加两次、状态混乱。在真实系统中表现为「机器人偶尔在两个航点之间来回摆动」，极难通过现场观察定位。组件测试 + 假导航器让它在 0.5 秒内稳定复现。

测试中还发现的规格问题

写用例时会遇到几个「代码这样做，但不知道是否正确」的行为：失败后重新 start，lap 不清零，message 仍保留上次的失败信息；巡逻中节点重启，进度全部丢失。这些不是明确的缺陷，而是需求未定义。把它们整理成问题清单交给产品确认，是测试工程师的重要产出。

T8.7 录包上的不变量检查

场景测试结束后，用 T5 的工具对录包做离线检查。巡逻中至少应满足两个不变量：线速度不超过 Nav2 控制器的上限；雷达最近距离始终大于安全阈值。

上限 0.26 m/s 对应第 13 章 Nav2 参数中控制器的 max_vel_x，请按你的实际配置修改。若开启了 E1（ros2_control），/cmd_vel 的类型是 TwistStamped，需要改为读取 msg.twist.linear.x。

T8.8 CI 流水线

CI 的现实约束

托管 CI 机器没有 GPU，仿真可能慢于实时，Gazebo 的 gpu_lidar 需要软件渲染（见 T4.2）。如果托管机器上无法稳定运行仿真，可以使用团队自己的带 GPU 的 runner（self-hosted runner）。各 action 的版本号请以官方仓库的最新发布为准。
