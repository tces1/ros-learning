T3　集成测试：launch_testing

组件测试在一个进程内验证逻辑；集成测试则像用户一样，把真实的节点作为独立进程启动，只通过话题、服务和参数与它交互。launch_testing 是 ROS2 官方的集成测试框架，能接入 colcon test，是机器人 CI 中最重要的一层。

阅读 + 动手约 3 小时测试篇前置：第 6 章、T2

本篇目标

  • 理解 launch_testing 的结构：启动描述、活动测试、关闭后测试
  • 断言进程输出、话题内容与频率、服务行为、退出码
  • 对 safety_stop 做黑盒测试，并验证接口契约（话题类型、QoS）
  • 对 launch 文件做冒烟测试，验证启动参数生效
  • 掌握测试隔离与消除不稳定测试的方法

T3.1 launch_testing 的结构

 test_xxx_launch.py
 ├─ generate_test_description()      ① 用 launch 描述「被测系统」：启动哪些节点、什么参数
 │     └─ ReadyToTest()                  所有进程启动后，开始运行测试
 ├─ class TestActive(unittest.TestCase)  ② 活动测试：被测节点运行期间执行
 │     └─ 可注入 proc_output、proc_info、以及 ① 返回的字典中的对象
 └─ @post_shutdown_test()               ③ 关闭后测试：所有进程退出后执行
       class TestAfter(unittest.TestCase)    典型用途：检查退出码

在 ament_python 包中，launch 测试文件放在 test/ 目录，文件名以 test_ 开头并带 @pytest.mark.launch_test 标记，colcon test 会通过 launch_testing 的 pytest 插件自动运行它。在 ament_cmake 包中则需要在 CMakeLists.txt 中注册（见 T3.7）。

T3.2 第一个集成测试：进程输出与退出码

退出码测试发现的缺陷

把上面的 talker 换成第 5 章的 mode_server 再跑一次，关闭后测试会失败：mode_server 的 main() 没有处理 Ctrl+C，收到 SIGINT 时抛出未捕获的异常并以非 0 退出码结束。

这看起来只是「退出时多了一段报错」，但在真实系统中会造成：launch 把它当成异常退出处理（可能触发 on_exit 关闭整个系统或重启）；退出时没有执行清理（没有停止电机、没有关闭文件，录包可能不完整）；日志里充满无关报错，掩盖真正的问题。修复方式是统一使用下面的入口写法：

团队里可以约定：每个节点都必须有一个 launch 测试，至少包含「启动后 N 秒内未崩溃」和「SIGINT 后退出码为 0」两项。成本很低，却能拦住大量启动崩溃和退出异常问题。

集成测试要面对「最终一致」

消息在进程间传递有延迟，前几条输出可能还是上一状态的结果。所以断言最后几条（out[-5:]），而不是第一条。如果业务对响应时间有要求（例如「检测到障碍后 100 ms 内停车」），就把它写成单独的延迟测试（见 T6），而不是在功能测试里隐式依赖时序。

统计不稳定测试

怀疑某个测试不稳定时，在本地连续运行它几十次：for i in $(seq 1 30); do launch_test test/test_safety_stop_launch.py || echo "FAIL $i"; done。不稳定测试比没有测试更糟：它会让团队习惯性地忽略红色 CI。

T3.8 launch_pytest：另一种写法

较新的 ROS2 版本还提供 launch_pytest，用 pytest 的夹具风格代替 unittest 类，适合偏好 pytest 的团队。概念相同：一个夹具返回 LaunchDescription，测试函数中断言输出和行为。两者可以在同一个项目中共存，新项目任选其一并保持一致即可。具体写法见 launch_pytest 示例。

自测题

1. 活动测试和关闭后测试分别适合检查什么？
活动测试在被测进程运行时执行，适合检查输出、话题、服务等运行期行为；关闭后测试在所有进程退出后执行，适合检查退出码、退出时的日志、生成的文件（如录包是否完整）。
2. 为什么话题测试中不能断言「收到的第一条消息是 #0」？
探针节点完成发现需要时间，默认的 VOLATILE 持久性不会给新订阅者补发历史消息，开头几条可能丢失。测试应该断言与发现时序无关的性质，例如序号连续、频率正确。
3. 测试 safety_stop 时，为什么要检查 /scan 订阅的 QoS？
真实雷达驱动通常以 BEST_EFFORT 发布。如果订阅端误用 RELIABLE，两者不兼容，节点将收不到任何雷达数据，并且没有报错。功能测试中测试发布者用的是兼容的 QoS，测不出这个问题，必须显式检查接口契约。
4. CI 中的 launch 测试偶发失败，你会按什么顺序排查？
先看失败日志中实际收到了什么（是没收到还是收到了错误值）；再检查是否有固定 sleep、是否等待了发现；然后检查 ROS_DOMAIN_ID 隔离和并行测试干扰；最后检查超时设置是否适应 CI 机器负载。必要时本地循环运行复现。
