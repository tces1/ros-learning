T1　机器人测试岗位与测试体系

机器人测试不是「把软件测试搬到机器人上」。被测系统有物理运动、传感器噪声、时间敏感性和安全风险。本篇先建立全局认识：机器人测试工程师测什么、在哪里测、怎么分层，以及 ROS2 生态里有哪些测试工具。

阅读约 1 小时测试篇建议与第 1–3 章同周学习

本篇目标

  • 说清机器人测试和 Web / 后端测试的关键差异
  • 掌握机器人测试的分层：单元、组件、集成、仿真、回放、台架、实机、现场
  • 知道每一层在 ROS2 中用什么工具实现
  • 了解机器人测试岗位的职责和常见质量指标

T1.1 机器人测试有什么不同

维度Web / 后端系统ROS2 机器人系统对测试的影响
输入确定的请求有噪声的传感器数据，每次都不一样判定不能要求「完全相等」，要用容差、统计和不变量
输出数据、页面速度、力矩，最终变成物理运动错误可能造成碰撞和伤害，实机测试必须有安全措施
时间大多与时间无关控制回路要求固定频率，数据要按时间戳对齐延迟、抖动、时钟（仿真时间 / 系统时间）本身就是测试对象
并发请求级并发几十个进程、上百个话题异步通信启动顺序、竞态、丢消息、QoS 不匹配是高频缺陷
环境服务器环境相对固定光照、地面、障碍物、网络千变万化需要「环境矩阵」和大量场景，仿真无法完全替代实机
复现日志 + 请求即可复现同样的操作在现场可能 10 次出 1 次问题必须录包（rosbag）；结论要用成功率表达
结果判定断言返回值「到达了吗？」「离障碍物多近？」「算安全吗？」测试预言（oracle）的设计本身是难点
测试预言（test oracle）

判断一次测试「通过还是失败」的依据。对一个排序函数，预言是「输出有序」；对导航，预言可能是「60 秒内到达目标 0.25 m 范围内，全程与障碍物距离不小于 0.15 m」。机器人测试中，写出可量化、可自动判定的预言往往比写测试代码更难，也更有价值。

T1.2 测试分层：从代码到现场

经典的「测试金字塔」在机器人领域扩展成下面这样。越往下越快、越便宜、越稳定；越往上越真实、越贵、越慢。

                    ▲ 真实度高、成本高、慢、结果有波动
                    │
   L7 现场测试       │  客户真实场地，真实任务，长时间运行
   L6 实机测试       │  实验室 / 测试场中的真机，按用例执行
   L5 台架测试 HIL   │  真实控制器 + 真实电机 / 传感器，车轮架空
   L4 回放测试       │  用录制的真实传感器数据驱动软件（rosbag）
   L3 仿真场景测试   │  Gazebo 中跑完整软件栈，批量场景
   L2 集成测试       │  启动多个真实节点，黑盒验证话题 / 服务（launch_testing）
   L1 组件测试       │  在测试进程内创建节点，直接调用回调或用假依赖
   L0 单元测试       │  纯函数、纯类，不依赖 ROS（pytest / gtest）
                    │
                    ▼ 快、便宜、确定性高、每次提交都跑
层级典型耗时运行频率能发现的缺陷本教材
L0 单元毫秒每次提交算法错误、边界条件、角度归一化、单位换算第 10 章、T2
L1 组件秒每次提交回调逻辑、状态机、参数处理、错误处理T2
L2 集成十几秒每次提交话题名 / 类型 / QoS 不匹配、启动失败、退出异常、接口契约T3
L3 仿真场景分钟每晚 / 合并前导航失败、碰撞、卡死、参数调优退化、TF 问题T4
L4 回放分钟每晚 / 修复缺陷时真实数据下的感知 / 定位问题，现场问题复现T5
L5 台架小时版本发布前驱动、通信、实时性、硬件时序T7
L6 实机小时到天版本发布前动力学、传感器特性、仿真与现实差距T7
L7 现场天到周交付 / 试点环境多样性、长期稳定性、人机交互T7
测试左移

每个在实机上发现的缺陷，都应该问一句：「能不能在更低的层级抓住它？」能的话就补一个低层测试。例如现场发现「雷达数据中有 NaN 时节点崩溃」，修复后应补一个 L0 单元测试和一个 L4 回放测试。这样同样的问题以后在提交代码时就会被拦住。

T1.3 SIL、HIL 与实机

名称全称含义ROS2 中的实现
MILModel-in-the-Loop用数学模型验证算法（常见于控制算法）Python / MATLAB 脚本，或单元测试中的简化模型
SILSoftware-in-the-Loop真实软件 + 仿真环境Gazebo + 全部 ROS2 节点（T4）；bag 回放（T5）
HILHardware-in-the-Loop真实控制硬件 + 仿真或台架负载真实工控机 / 驱动板 + 架空的电机，或仿真器通过真实总线发数据（T7）
实机Vehicle / Robot test整机在真实环境运行按测试计划执行用例并录包（T7）

T1.5 一个缺陷从现场到回归测试的生命周期

 现场：机器人在走廊转角处停住不动（10 次中出现 2 次）
   │
   ├─ 1. 记录：时间点、软件版本（git SHA）、参数、地图，导出事故前后 60 s 的 bag
   ├─ 2. 分析：PlotJuggler / Foxglove 看 /cmd_vel、/scan、代价地图、行为树日志
   ├─ 3. 复现：本地用 bag 回放（T5）或在仿真中搭出相同转角（T4）
   ├─ 4. 定位：开发修复（例如局部代价地图膨胀半径过大）
   ├─ 5. 回归测试：把场景加入仿真场景库 / 把 bag 加入回放回归集
   └─ 6. 验证：仿真 20 次 + 实机 10 次，成功率达到准入标准后关闭缺陷

T1.6 常用质量指标

指标定义典型用途
任务成功率成功次数 / 总次数导航、抓取等任务级验收
MDBF平均故障间隔里程（Mean Distance Between Failures）移动机器人可靠性
MTBF平均故障间隔时间长期运行稳定性
人工干预率每小时（或每公里）需要人工接管的次数自主性评估
定位误差估计位姿与真值的距离和角度差定位模块验收
到点精度到达后与目标位姿的偏差导航、对接充电
端到端延迟传感器数据产生到控制指令发出的时间避障响应能力
话题频率与抖动实际发布频率、间隔的标准差传感器、控制回路健康度
资源占用CPU、内存、内存增长斜率长稳测试、硬件选型
缺陷逃逸率在更高层级（尤其现场）才发现的缺陷占比衡量测试体系本身的有效性

T1.7 机器人测试工程师的职责

方向主要工作开发背景的优势
测试开发搭建测试框架、编写自动化测试、维护 CI、开发仿真场景和数据分析工具直接复用编程能力；能读懂被测代码，写出更有针对性的测试
系统 / 集成测试整机功能验证、版本验收、回归测试、性能与长稳能看懂日志和源码，定位问题更快
实机 / 现场测试制定测试计划，执行实机用例，管理测试场地和安全，收集现场数据能写脚本自动化数据采集和分析
质量与流程测试策略、准入准出标准、缺陷管理、质量度量理解开发流程，能推动测试左移
有开发经验的人最容易忽略的三件事

1）统计思维：机器人测试结论几乎都是「成功率 x%（n 次）」，跑一次成功不代表没问题。2）安全意识：实机测试前先验证急停，再验证功能。3）数据意识：没有录包的失败几乎无法分析，「先录包再测试」要成为肌肉记忆。

自测题

1. 为什么机器人测试的结论通常要写成「成功率」而不是「通过 / 不通过」？
传感器噪声、时序、仿真物理引擎的随机性都会让同一个用例的结果有波动。只跑一次无法区分「必然成功」和「碰巧成功」，需要重复 n 次并报告成功率，必要时给出置信区间（见 T7）。
2. 现场发现「雷达偶发全 0 数据导致机器人急停」，修复后应在哪些层级补测试？
L0：对处理雷达数据的函数补边界用例（全 0、NaN、inf）；L4：把现场 bag 中出问题的片段加入回放回归集；必要时 L3：在仿真中注入异常雷达数据。目标是以后同类问题在提交代码阶段就被拦住。
3. SIL 和 HIL 的区别是什么？
SIL 中所有软件运行在普通电脑上，环境和硬件由仿真提供；HIL 中使用真实的控制硬件（工控机、驱动板、传感器等），只有部分环境或负载是仿真或台架提供的，能发现驱动、总线、实时性相关的问题。
4. 给「点到点导航」写一个可自动判定的测试预言。
示例：Nav2 返回 SUCCEEDED；用时 ≤ 60 s；终点位置误差 ≤ 0.25 m、朝向误差 ≤ 0.3 rad；全程雷达最近距离 ≥ 0.15 m；全程没有超过 5 s 的「速度为 0 且未到达」状态。每一项都能从话题数据中自动计算。

自查清单

  • 能说出机器人测试和 Web 测试的至少 5 个差异
  • 能画出 L0–L7 测试分层，并说出每层的工具
  • 理解测试预言的概念，能为一个导航任务写出量化判定标准
  • 知道 MDBF、人工干预率、端到端延迟等指标的含义
