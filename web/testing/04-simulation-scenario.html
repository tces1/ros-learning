T4　仿真与场景测试

单个节点都没问题，不代表整机能完成任务。仿真场景测试把完整软件栈（Gazebo + Nav2 + 业务节点）放进一个个精心设计的场景中，自动判定成败，并重复运行统计成功率。它是导航、规划类功能回归测试的主力，也是机器人测试开发岗位最核心的技能之一。

阅读 + 动手约 4 小时测试篇前置：第 9、13 章、T3

本篇目标

  • 理解仿真测试能测什么、不能测什么
  • 以无界面模式运行 Gazebo，适配 CI
  • 用 YAML 描述场景（起点、障碍物、目标、判定准则），批量运行
  • 编写自动判定的场景执行器：到达、超时、到点误差、安全距离、停滞
  • 用成功率和置信区间报告结果，识别不稳定的场景

T4.1 仿真测试的能力边界

仿真擅长仿真不擅长
导航、规划、行为逻辑的回归（参数改了有没有变差）真实传感器噪声、反光、玻璃、黑色物体、阳光干扰
大量重复运行、统计成功率轮子打滑、地面不平、电机饱和等动力学细节
危险场景（贴近障碍、急停、悬崖）的安全验证硬件时序、驱动、总线通信问题
构造现场难以复现的场景（特定障碍布局、故障注入）计算资源受限下的实时性（仿真机器性能通常远好于机器人）
在 CI 中无人值守运行人与机器人的真实交互
仿真与现实的差距（sim-to-real gap）

仿真通过不代表实机通过，但仿真失败基本意味着实机也会失败。所以仿真测试最大的价值是「便宜地拦住明显的回归」，把昂贵的实机时间留给仿真无法覆盖的问题。

gpu_lidar 和相机依赖渲染引擎。在没有 GPU 的容器中通常需要 Mesa 软件渲染（安装 libegl1、mesa-utils 等），速度会明显变慢，仿真实时因子（RTF）可能低于 1。判定准则中的时间要用仿真时间计算，不能用墙钟时间。

T4.5 场景执行器

执行器是一个普通的 Python 程序：读取场景、设置初始位姿、依次发送目标、在等待期间持续监控，最后对照判定准则给出结论，写出 JSON 结果，并以退出码表示成败。

判定数据从哪里来

这里用 AMCL 的估计位姿判断「到点误差」，它本身也可能有误差。更严格的做法是从 Gazebo 获取真值位姿（例如在模型上加 PosePublisher 插件并桥接到 ROS），同时报告「定位误差 = AMCL − 真值」。测试预言的数据源本身是否可信，是设计测试时必须考虑的问题。

T4.8 不稳定场景的来源与对策

来源表现对策
启动竞态偶发「Nav2 未激活」「TF 不存在」用 waitUntilNav2Active 等条件等待，而不是只靠 TimerAction 延时
实时因子波动CI 上超时，本地通过所有时间判定用仿真时间；记录 RTF；CI 机器资源固定
物理与传感器随机性同一场景时过时不过这是真实特性，不是测试的错：用成功率和准入阈值表达
残留进程第二次运行开始失败每次运行后清理 gz 进程；CI 中每批使用新容器
场景本身不合理障碍物与墙重叠、目标点在膨胀区内新场景先在界面模式下人工确认一次再入库
不要通过「重跑直到通过」让 CI 变绿

机器人测试中「偶发失败」往往正是现场会出现的问题。正确做法是把成功率作为指标长期跟踪：一个场景从 95% 降到 80%，比任何单次失败都更能说明某次修改引入了回归。

自测题

1. 为什么判定超时要用仿真时间？
CI 机器性能不同、负载不同，仿真实时因子可能小于 1。用墙钟时间判定会把「机器慢」误判为「机器人慢」。机器人在仿真世界中花了多少时间，才是要评估的指标。
2. 一个场景跑了 5 次全部通过，能说它的成功率达到 95% 吗？
不能。5 次全过时，成功率 95% 置信区间的下限约为 57%。要以较高置信度说明成功率 ≥ 95%，需要几十次以上的无失败运行（按「三分之一规则」，0 次失败时 95% 上限的失败率约为 3/n，需要 n ≈ 60）。
3. 为什么场景库中要有期望「失败」的场景？
真实环境中一定会出现无法完成的任务。系统在这种情况下的行为（是否及时放弃、是否报告、是否安全）同样是需求的一部分，必须测试。只测正向场景，会漏掉无限重试、卡死、强行通过等严重问题。

自查清单

  • 能以无界面模式运行仿真，并确认传感器数据正常
  • 写出至少 4 个场景，包含一个负向场景
  • 场景执行器能输出 JSON 结果和正确的退出码
  • 批量运行后得到带置信下限的汇总表和 junit.xml
  • 能解释仿真测试的能力边界
