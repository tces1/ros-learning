2.1 软件分层

│ 你的应用：驱动 / 算法 / 业务节点                               │
├───────────────────────────────┬───────────────────────────┤
│ rclcpp（C++ 客户端库）          │ rclpy（Python 客户端库）     │  ← 你直接使用的 API
├───────────────────────────────┴───────────────────────────┤

├───────────────────────────────────────────────────────────┤
│ rmw（ROS MiddleWare 抽象接口）                               │
├──────────────┬──────────────┬──────────────┬──────────────┤
│ rmw_fastrtps │ rmw_cyclonedds│ rmw_connextdds│ rmw_zenoh    │  ← 可替换的中间件实现
├──────────────┴──────────────┴──────────────┴──────────────┤

DDS / Zenoh 实现真正收发数据、负责发现和 QoS出网络问题时需要了解

2.2 DDS 是什么

DDS（Data Distribution Service）是 OMG 组织制定的发布/订阅通信标准，广泛用于军工、航空、金融交易系统。ROS2 选用它的原因：

  • 去中心化发现：参与者通过 SPDP/SEDP 协议自动发现彼此，无需中心服务器
  • 丰富的 QoS：可靠性、历史深度、持久性、截止期、存活性等都可配置（第 4 章详解）
  • 成熟可靠：已有多家商业与开源实现，经过大规模工业验证
  • 共享内存传输：同一台机器上的进程间可走共享内存，避免网络栈开销

2.4 命名规则

节点、话题、服务、动作都有名字，ROS2 的名字解析规则必须掌握，否则多机器人、命名空间、重映射都会出错。

写法称为节点 /robot1/driver 中解析结果
/scan绝对名（全局）/scan
scan相对名/robot1/scan（加上节点的命名空间）
~/status私有名/robot1/driver/status（加上节点完整名）
写代码时优先使用相对名

相对名可以在启动时整体放进命名空间，实现「同一份代码启动多台机器人」。写死 /scan 这种绝对名会让多机器人场景无法工作。

命名约束：只能包含字母、数字、下划线和 /，不能以数字开头，不能有连续的 // 或 __。

2.5 发现机制与网络隔离

ROS_DOMAIN_ID

同一个局域网内，ROS_DOMAIN_ID 相同的节点会自动互相发现。默认值为 0。

实验室常见事故

多个人在同一 Wi-Fi 下都用默认 Domain 0，结果你的 /cmd_vel 开动了同学的机器人。务必给每个人或每台机器人分配不同的 Domain ID。

限制发现范围（Jazzy 起）

Humble 用户

Humble 中使用 export ROS_LOCALHOST_ONLY=1 达到「只在本机发现」的效果，该变量在 Jazzy 中已被弃用。

2.6 工作空间与包

包（Package）

包是 ROS 代码组织、构建、发布的最小单位。每个包都有 package.xml（元信息与依赖）以及构建描述文件。

my_robot_driver/                ament_cmake 包（C++ 为主）
├── package.xml                 包名、版本、依赖
├── CMakeLists.txt              构建规则
├── include/my_robot_driver/    头文件
├── src/                        源文件
├── launch/                     启动文件
└── config/                     参数 YAML

my_robot_tools/                 ament_python 包（纯 Python）
├── package.xml
├── setup.py                    安装规则与入口点
├── setup.cfg
├── resource/my_robot_tools     包标记文件
└── my_robot_tools/             Python 模块
    └── __init__.py

工作空间（Workspace）

~/ros2_ws/
├── src/        ← 你只在这里写代码（放多个包）
├── build/      ← 编译中间产物（可随时删除）
├── install/    ← 安装结果，source install/setup.bash 后生效
└── log/        ← 构建日志

Underlay 与 Overlay

ROS2 的环境是叠加的：先 source 系统安装的 ROS（underlay），再 source 你的工作空间（overlay）。overlay 中的同名包会覆盖 underlay 中的。

这意味着你可以把某个官方包（比如 nav2 的某个插件）的源码 clone 到自己的工作空间里修改，它会优先于系统版本被使用。

2.7 时间与时钟

时钟类型含义场景
ROS Time默认等于系统时间；若参数 use_sim_time=true，则跟随 /clock 话题绝大多数节点、消息时间戳
System Time系统墙上时钟日志、与外部系统交互
Steady Time单调递增，不受系统时间调整影响测量耗时、超时判断
仿真和回放 rosbag 时必须统一 use_sim_time

Gazebo 和 ros2 bag play --clock 会发布 /clock。若有的节点用仿真时间、有的用系统时间，TF 会报「外推到未来 / 过去」的错误，导航完全无法工作。

2.8 生命周期节点（Lifecycle / Managed Node）

普通节点一启动就开始工作。但在真实机器人上，我们常需要「先全部配置好、确认硬件就绪，再统一激活」。生命周期节点提供了一个标准状态机：

              configure            activate
 [Unconfigured] ───────► [Inactive] ───────► [Active]
       ▲   cleanup  │        ▲  deactivate     │
       └────────────┘        └─────────────────┘
          任意状态 ── shutdown ──► [Finalized]
状态应该做的事
Unconfigured刚创建，什么也不做
Inactive已读参数、分配内存、创建发布者，但不发布数据、不处理请求
Active正常工作
Finalized即将销毁

Nav2 的所有服务器都是生命周期节点，由 lifecycle_manager 按顺序统一管理，这就是为什么 Nav2 启动后要等一会儿才「Ready」。

2.9 组件（Component）与进程内通信

默认每个节点是一个独立进程，图像、点云这类大消息在进程间传递需要序列化和拷贝。组件是编译成共享库的节点，可以在运行时被加载到同一个「容器进程」中，启用进程内通信后可实现零拷贝。

第 6 章会介绍如何在 launch 文件中用 ComposableNodeContainer 组合节点。

计算图就是系统的「接口清单」。测试工程师可以把它当作基线：每个版本保存一份计算图快照，与上一版本对比，任何没有在变更说明中出现的节点、话题、类型变化都值得追问。

自测题

1. 节点 /arm/gripper 发布话题 ~/state、state 和 /state，完整名称分别是什么？
/arm/gripper/state、/arm/state、/state。
2. 你和同学在同一 Wi-Fi 下，你看到了陌生的 /turtle1/cmd_vel 话题，原因和解决办法？
双方使用了相同的 ROS_DOMAIN_ID（通常都是默认 0），DDS 自动发现了彼此。解决：各自设置不同的 ROS_DOMAIN_ID，或单机学习时设置 ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST（Humble 用 ROS_LOCALHOST_ONLY=1）。
3. 为什么相机驱动和图像处理节点适合做成组件放在同一进程？
图像数据量大（1080p RGB 一帧约 6 MB），跨进程传输需要序列化和内存拷贝，CPU 开销和延迟都高。放在同一容器并启用进程内通信，可以直接传递指针，实现零拷贝。
4. 生命周期节点处于 Inactive 状态时应该发布数据吗？
不应该。Inactive 表示已完成配置但尚未激活，此时发布者已创建但不应发布数据，也不应处理服务请求。只有在 Active 状态下才开始正常工作。
