第 12 章　ros2_control

ros2_control 把「控制算法」和「硬件读写」解耦：同一套控制器既能驱动 Gazebo 中的仿真车，也能驱动真实电机，只需更换硬件插件。本章把小车改造为使用 ros2_control，并介绍如何为真实硬件编写接口。

阅读 + 动手约 3–4 小时进阶

本章目标

  • 理解 controller_manager、硬件接口、控制器三者的关系
  • 在 URDF 中声明 <ros2_control> 标签

  • 在 Gazebo 中通过 gz_ros2_control 运行

12.1 为什么需要 ros2_control

第 9 章中我们使用 Gazebo 自带的 DiffDrive 插件，它只能在仿真里用。换成真实机器人时，需要另写一个驱动节点来订阅 /cmd_vel、计算轮速、读编码器、发布里程计——这部分逻辑与仿真插件重复，且两边行为可能不一致。

ros2_control 的思路：

             /diff_drive_controller/cmd_vel                    /joint_states
                         │                                          ▲
                         ▼                                          │
 ┌───────────────────── controller_manager（实时循环，如 50 Hz）──────────────────┐
 │   ┌──────────────────────────┐        ┌──────────────────────────────┐      │
 │   │ diff_drive_controller     │        │ joint_state_broadcaster      │      │  ← 控制器（与硬件无关）
 │   │ 速度 → 左右轮角速度 + 里程计 │        │ 读取关节状态并发布             │      │
 │   └──────────┬───────────────┘        └──────────────▲───────────────┘      │
 │       command interfaces（velocity）     state interfaces（position, velocity） │
 │   ┌──────────▼────────────────────────────────────────┴───────────────┐      │
 │   │          Resource Manager：管理所有硬件接口                          │      │
 │   └──────────┬─────────────────────────────────────────────────────────┘      │
 └──────────────┼──────────────────────────────────────────────────────────────────┘
                ▼   read() / write()
   ┌──────────────────────┬─────────────────────────┬──────────────────────────┐
   │ gz_ros2_control      │ mock_components         │ 你的串口 / CAN 驱动插件     │  ← 硬件接口（可替换）
   │ （Gazebo 仿真）        │ （无硬件测试）            │ （真实机器人）              │
   └──────────────────────┴─────────────────────────┴──────────────────────────┘
组件职责
controller_manager按固定频率循环：read() 硬件 → update() 控制器 → write() 硬件；管理控制器的加载、激活、切换
硬件接口（Hardware Interface）暴露 state interface（可读：位置、速度、力矩）和 command interface（可写：速度、位置、力矩）
控制器（Controller）读取 state、计算并写入 command，同时提供 ROS 话题 / 动作接口

运行与遥控

Twist 还是 TwistStamped

Jazzy 起 diff_drive_controller 只接受 geometry_msgs/msg/TwistStamped，里程计发布在 /diff_drive_controller/odom。与 Nav2 联用时，需在 Nav2 参数中开启带时间戳的速度指令（enable_stamped_cmd_vel: true），并把 /cmd_vel 重映射到控制器话题。话题类型不匹配时不会报错，只是车不动——用 ros2 topic info -v 检查。

12.6 controller_manager 命令

控制器同样有生命周期：unconfigured → inactive → active。一个 command interface 同一时刻只能被一个 active 控制器占用，切换控制器即可在「自动驾驶」和「手动」模式间切换。

测试视角

ros2_control 处在软件与硬件的交界处，是安全相关缺陷最集中的地方之一。

测试点方法期望
无硬件测试控制器使用 mock_components/GenericSystem 作为硬件控制器加载、激活、指令与状态接口正常；可在 CI 中运行
指令超时持续发送速度后停止发送diff_drive_controller 在 cmd_vel_timeout 内输出零速

控制频率controller_manager 的 update_rate 与实际周期满负载下周期抖动在要求范围内（T6）
指令超时必须验证

上游节点崩溃或网络中断时，如果底盘继续执行最后一条速度指令，机器人会失控。这是实机测试前必须在台架上验证的项目，详见 T6 故障注入 和 T7 台架测试。

自测题

1. 为什么在 ros2_control 模式下要移除 Gazebo 的 DiffDrive 插件和 /odom、/tf 桥接？
否则会有两套系统同时控制车轮、同时发布 odom→base_footprint 的 TF，导致冲突与跳变。ros2_control 模式下这些都由 diff_drive_controller 和 joint_state_broadcaster 提供。
2. cmd_vel_timeout 有什么作用？
安全保护：上层节点崩溃或网络中断导致长时间收不到指令时，控制器自动把速度设为 0，防止机器人带着最后一个速度指令冲出去。
3. 同一个车轮的 velocity command interface 能同时被两个控制器使用吗？
不能。资源管理器保证一个 command interface 同时只被一个 active 控制器占用（claimed）。需要切换时用 switch_controllers。
