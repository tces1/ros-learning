9.1 Gazebo 与 ROS2

Gazebo 是独立的仿真器，有自己的通信系统（gz-transport）和消息格式（gz.msgs）。它和 ROS2 之间通过 ros_gz_bridge 转换消息。

 ┌────────────── Gazebo Harmonic ───────────────┐          ┌──────────── ROS2 ────────────┐
 │  DiffDrive 插件 ◄── gz /cmd_vel ─────────────┼─ bridge ─┼── /cmd_vel ◄── teleop / Nav2 │
 │  DiffDrive 插件 ──► gz /odom, /tf ───────────┼─ bridge ─┼──► /odom, /tf                │
 │  JointStatePub  ──► gz /joint_states ────────┼─ bridge ─┼──► /joint_states ──► RSP     │
 │  gpu_lidar 传感器 ──► gz /scan ──────────────┼─ bridge ─┼──► /scan ──► RViz / SLAM    │
 │  仿真时钟        ──► gz /clock ──────────────┼─ bridge ─┼──► /clock                    │
 └──────────────────────────────────────────────┘          └──────────────────────────────┘

为什么需要 gz_frame_id

Gazebo 加载 URDF 时会把固定关节连接的 link 合并（laser_link 被并入 base_link），所以默认发出的 scan 消息 frame_id 不是 laser_link。gz_frame_id 强制指定 frame_id，保证与 TF 树一致。

车轮在 RViz 中显示为红色 / 不转/joint_states 未桥接或 JointStatePublisher 插件未加载

自测题

1. 为什么启动仿真时所有 ROS 节点都要设置 use_sim_time: True？
Gazebo 的消息时间戳是仿真时间（从 0 开始，且可能慢于真实时间）。若节点用系统时间，它查询 TF 或比较时间戳时会与数据相差几十年，导致 TF 外推错误、数据被丢弃。
2. odom → base_footprint 的 TF 由谁发布？base_footprint → laser_link 呢？
前者由 Gazebo 的 DiffDrive 插件计算并通过 bridge 发布到 /tf；后者由 robot_state_publisher 根据 URDF 的固定关节发布到 /tf_static。
3. 第 8 章用的 joint_state_publisher_gui 在仿真中还需要吗？
不需要，而且不能同时运行。仿真中关节状态来自 Gazebo 的 JointStatePublisher 插件，两者同时发布会冲突。

自查清单

  • Gazebo 中能看到房间和小车
  • 键盘可以控制小车运动
  • /scan 10 Hz、/odom 30 Hz、/clock 均有数据
  • RViz 中激光点贴合墙壁，TF 树完整
  • 会用 gz topic 命令定位桥接问题
